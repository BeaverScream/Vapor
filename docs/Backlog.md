## Admin: Security

- [ ] **BL-ADMIN-URL-OBSCURE-01** Admin endpoint pre-production hardening: path obscuration and bundle token removal ⚠️ Pre-production required
  *(BL-ADMIN-TOKEN-SECURITY-01 merged into this item)*
  - **Current Issue:** Two independent pre-production security gaps exist on the admin endpoint. First, the admin dashboard path defaults to a well-known convention (e.g., `/admin` in the current development setup) — anyone probing standard paths reaches the auth prompt and can attempt credential attacks. Second, `ADMIN_API_TOKEN` is compiled into the Vite client bundle via `define: { 'import.meta.env.VITE_ADMIN_TOKEN': ... }`, making the credential visible to any visitor who fetches the bundle. Both are acceptable trade-offs for solo local development but must be resolved before any public deployment.
  - **Why:** Obscuring the path removes the ability to discover the auth prompt at all without insider knowledge (defense-in-depth); removing the token from the bundle ensures the credential is not exposed in JS source even if the path is later discovered. Neither fix replaces proper auth (VP-6.2 or BL-ADMIN-AUTH-AND-01), but both are required before Vapor is deployed to a publicly accessible host.
  - **Expected Outcome:** The admin route in the backend router and React frontend is renamed to a configurable, non-guessable path via an env var (e.g., `ADMIN_PATH=/vapor-ops-7x3k`); the default must not be a well-known path. `VITE_ADMIN_TOKEN` is removed from `vite.config.ts` and the `ImportMetaEnv` declaration in `vite-env.d.ts`; `AdminDashboard.tsx` falls back to `localStorage` (persisted manual entry) then the manual credential form. Operators can optionally bookmark the configured admin URL with the token as a query param (stripped on load) for one-click convenience without bundling it. ADMIN_SETUP.md documents both changes.

- [ ] **BL-ADMIN-AUTH-AND-01** Require both Bearer token AND Basic credentials simultaneously
  - **Current Issue:** The admin auth middleware (`requireAdminAuth`) accepts a request if it satisfies *either* Bearer token or HTTP Basic auth — an OR gate. A deployment that configures both methods cannot enforce that a caller must supply both simultaneously, which limits the security benefit of having two credentials.
  - **Why:** Requiring both factors (token + username/password) hardens the admin endpoint against credential leakage: compromise of either credential alone is insufficient. This is the natural upgrade path once the current OR-gate design has been validated in operation.
  - **Expected Outcome:** `requireAdminAuth` is rewritten with an AND gate: if `ADMIN_API_TOKEN` is set, the request must supply a valid Bearer token; if `ADMIN_BASIC_USER`/`ADMIN_BASIC_PASS` are also set, the request must additionally supply valid Basic credentials. A request that satisfies only one factor when both are configured is rejected with 401. Single-factor deployments (only one auth block configured) continue to work as today.

## Admin: Observability & Alerting

- [ ] **BL-ADMIN-ALERT-01** Threshold-based real-time alerting
  - **Current Issue:** The admin observability layer is entirely retrospective. The live dashboard polls every 30 seconds and scheduled reports arrive daily — but there is no mechanism to notify the operator when a metric crosses a critical threshold in real time. A heap spike to 90%, a sudden 10× surge in `RATE_LIMITED` errors, or a blocklist that doubles in size are all invisible until the next periodic report lands in the inbox.
  - **Why:** Retrospective reporting is useful for trend analysis but useless for incident response. By the time a daily email arrives describing a heap spike that happened at 2 AM, the server may have already crashed or been restarted. Proactive alerting closes the gap between "something went wrong" and "operator is aware," which is the minimum bar for a production observability layer.
  - **Expected Outcome:** A configurable threshold table (defined via env vars or a small config block) maps metric fields to alert thresholds — e.g. `ALERT_HEAP_MB=400`, `ALERT_RATE_LIMITED_PER_PERIOD=50`. On each scheduler flush tick, threshold checks run after the row is written. Any breach triggers an immediate one-off alert email (subject: `[Vapor] ALERT — <metric> threshold breached`) distinct from the periodic report format. Alerts are de-bounced — a breach that persists across consecutive ticks sends only one email per hour, not one per flush. No new dependencies required; the existing Nodemailer transport is reused.

- [ ] **BL-SCHEDULER-MIDNIGHT-01** Silent report skip on server restart after midnight crossing
  - **Current Issue:** `checkReports` in `scheduler.ts` detects a midnight crossing by comparing `lastReportDate` (set on the first tick after `start()`) to the current UTC date on each subsequent tick. If the server restarts after UTC midnight but before the first tick fires, `lastReportDate` is initialized to today — the crossing is never detected and the daily (and potentially weekly/monthly) report for the previous period is silently skipped. The raw data exists in the CSV store, but the aggregation and email are never triggered.
  - **Why:** Scheduled reports are the primary mechanism for long-term operational visibility (see BL-ADMIN-RETRY-01 for the related SMTP failure gap). A restart at any point between midnight and the first post-startup tick — which is at least 60 seconds and up to `METRICS_FLUSH_INTERVAL_MS` (30 minutes) — causes a permanent gap. This is invisible to the operator: no error is logged, no email is sent, and no indication is given that the report was missed.
  - **Expected Outcome:** On `start()`, compare the current UTC date against the most recent `processStartedAt` written in the store (or the last written row's `recordedAt`). If a crossing is detected, trigger the missed reports immediately before the warm-up delay fires. Alternatively, persist `lastReportDate` to a small sidecar file so restarts restore the correct baseline. The fix must not cause duplicate reports if the server restarts multiple times within the same UTC day.
  - **Scope note (added 2026-06-11, R2 review):** The gap is slightly wider than the restart case — when *multiple* midnights pass between ticks (clock suspension, container pause), `checkReports` generates a daily report only for `lastReportDate`; intermediate days are skipped silently. The fix should cover the multi-day case by iterating each missed day, not just the most recent one.

- [ ] **BL-ADMIN-RETRY-01** Report delivery failure recovery
  - **Current Issue:** `sendReportEmail` is fire-and-forget. If Gmail SMTP is unreachable at the exact moment a daily, weekly, or monthly report is triggered (network blip, Gmail outage, expired app password), the report is silently dropped with only a `console.error` log line. There is no retry, no local fallback, and no way to discover the failure after the fact — the operator simply never receives that period's report.
  - **Why:** Scheduled reports are the primary mechanism for long-term operational visibility. A single SMTP failure at midnight means a permanent gap in the historical record for that period — the data existed in the store, but the aggregation was discarded. Silent failures that require no action from the operator are the hardest class of bug to notice; the cost of a missed report only becomes visible weeks later when trends look incomplete.
  - **Expected Outcome:** When `sendReportEmail` encounters an SMTP error, the failed `PeriodAggregate` payload is serialized to a small local "pending reports" file (e.g. `pending_reports.json`) alongside the CSV store. On the next scheduler flush tick — and once on server startup — the pending file is checked; any unsent reports are retried. After two consecutive failed retries the entry is abandoned and logged with a structured error so it is visible in server logs. Successful delivery removes the entry from the pending file. The pending file contains only aggregated `PeriodAggregate` data — no raw row data, no user fields.

## Admin: Reporting & Email

- [ ] **BL-REPORT-MONTH-01** Monthly report date anchor diverges between the manual trigger endpoint and the scheduler
  - **Current Issue:** `POST /admin/report/monthly` in `routes.ts` computes the previous month using `now.getUTCMonth()` anchored to the current wall-clock time (can be called any day of the month). The scheduler's `checkReports` in `scheduler.ts` computes the previous month using `crossedDay.getUTCMonth()` anchored to the 1st of the new month (always the day midnight was crossed). Both use the same `getUTCMonth() - 1` arithmetic, which produces the correct answer in both cases today but via structurally different reference dates. A future change (e.g. adding a `?month=` query param to the endpoint) is likely to copy the wrong pattern.
  - **Why:** Duplicated date math with different anchor semantics is a latent bug surface. The divergence also makes it impossible to reproduce a specific past month's report via the HTTP endpoint if the caller is not aware of the wall-clock anchor assumption.
  - **Expected Outcome:** Extract a `getPrevMonthYear(date: Date): { month: number; year: number }` helper (1-indexed month output) used by both `routes.ts` and `scheduler.ts`. Both callers pass their respective anchor date. The arithmetic lives in one place.
  - **Scope extension (added 2026-06-11, R2 review):** The same divergence family exists for the daily and weekly anchors. The manual weekly trigger in `routes.ts` was patched on 2026-06-11 to be Monday-aligned, but the date math is still duplicated between `routes.ts` and `scheduler.ts`. Extract the full helper set — `getPrevDay(date)`, `getPrevMonday(date)`, `getPrevMonthYear(date)` — and use it from both call sites. This also makes T6.5-10 genuinely testable: today it asserts on an inline re-implementation of the January-rollover ternary and can never catch a regression in `scheduler.ts`; once the helper exists, the test should call the real function.

- [ ] **BL-REPORT-WEEKLY-MONTHLY-01** Weekly and monthly report emails contain empty/zeroed metrics
  - **Current Issue:** Triggering a weekly or monthly report via the admin dashboard sends an email, but all reported metrics are zero or empty — as if no rows exist for the period. The daily report works correctly over the same data. Observed during manual E2E testing (T6.8-11).
  - **Why:** Operators cannot use weekly or monthly reports for trend analysis if the data is always empty. The failure also masks bugs in the date-range query logic for ranges longer than one day, since a broken query silently returns zero rows rather than raising an error.
  - **Expected Outcome:** Weekly and monthly report generators correctly query the CSV store for rows within the previous week (Monday–Sunday UTC) and previous calendar month respectively, aggregate them, and produce non-empty email bodies when data exists. The root cause — likely an off-by-one in the UTC midnight boundary calculation or a date anchor mismatch (see BL-REPORT-MONTH-01) — is identified and fixed. A regression test covers weekly and monthly aggregation against a fixed row set that spans multiple days.
  - **Note:** Fix BL-REPORT-MONTH-01 first — it is the likely root cause of this item. Verify whether this item is fully resolved as a side-effect before implementing a separate fix here.

- [ ] **BL-EMAIL-METRICS-MISMATCH-01** Email body metric summary displays incorrect values while the CSV attachment for the same report is correct
  - **Current Issue:** Manual E2E testing found that most fields in the email body metric summary are wrong. Only rooms created, avg RSS used, peak RSS used, and restart count appear correct. The CSV attachment for the same report shows correct values for all fields. This confirms the bug is in `buildEmailHtml` or how `PeriodAggregate` is passed to it — not in the underlying data collection or CSV serialization.
  - **Why:** The email body is the most visible output of the reporting system. If its summary values are wrong, operators are misled by the report they actually read. The CSV being correct while the HTML is wrong is an invisible split — an operator with no reason to cross-check the two would act on incorrect information.
  - **Expected Outcome:** Identify which fields in `buildEmailHtml` read from wrong `PeriodAggregate` properties, apply incorrect unit conversions, or are missing from the template entirely. Fix the template so all displayed metrics match the CSV attachment for the same period. Add or extend a unit test asserting `buildEmailHtml` renders correct values for every displayed field given a known `PeriodAggregate` input (extends `T6.7-08`).

- [ ] **BL-METRICS-PEAK-DISPLAY-01** Remove `peakRooms`/`peakParticipants` from CSV rows; surface daily peaks in the email body metric summary instead
  - **Current Issue:** The CSV attachment includes `peakRooms` and `peakParticipants` columns in every periodic row. Per-interval peaks are not actionable in a raw data file — what operators need is the single highest concurrent count across the full day. The email body metric summary currently does not display daily peaks at all.
  - **Why:** Per-interval peak values in a CSV row add noise without insight. The meaningful figure is the daily peak — the highest concurrent room and participant count recorded at any point during the reporting period. That belongs in the email summary where it is immediately visible, not buried across dozens of CSV rows that must be manually max'd.
  - **Expected Outcome:** Remove `peakRooms` and `peakParticipants` from the `PeriodicRow` type and the CSV column list. `computeAggregate` derives `peakRooms` and `peakParticipants` by taking `max` across all rows in the period (sourced from the period peak values before the field is removed from the row type). `buildEmailHtml` includes "Peak concurrent rooms" and "Peak concurrent participants" in the metric summary section. No changes to the live `/admin/metrics` snapshot, which retains all-time peaks.

## Analytics Store

Items in this section apply to the CSV backend. BL-ANALYTICS-02 is the long-term replacement for all CSV-specific work — evaluate it first before prioritizing other items in this section.

- [ ] **BL-ANALYTICS-02** Supabase Analytics Store migration
  - **Current Issue:** `CsvAnalyticsStore` is the only analytics backend. CSV has no indexing, no cross-day range queries without reading multiple files, and no durability across server migrations or container replacements. Phase 6.4 explicitly deferred a `SupabaseAnalyticsStore` implementation with the note "swap at the construction site only" — but without a tracked backlog item, that intent has no path to execution.
  - **Why:** The `AnalyticsStore` interface was deliberately designed to be backend-agnostic so the swap would be zero-risk. Supabase provides indexed time-range queries (eliminating full-file reads), survives server restarts and redeployments without data loss, and enables future multi-instance aggregation. Staying on CSV past the early operational phase means accepting degraded query performance and fragile persistence in exchange for no engineering gain.
  - **Expected Outcome:** A `SupabaseAnalyticsStore` class that satisfies the existing `AnalyticsStore` interface (`writeSnapshot`, `queryRows`, `close`) with no changes to the scheduler, report generators, or any callers. The store is selected at server startup via an env var (e.g. `ANALYTICS_BACKEND=supabase|csv`). `CsvAnalyticsStore` remains as a fallback for local development. One-time migration tooling to bulk-load existing CSV rows into the Supabase table is included.

- [ ] **BL-ANALYTICS-01** CSV file rotation (daily) and disk janitor (monthly)
  - **Current Issue:** `CsvAnalyticsStore` writes all records to a single, fixed file path for the lifetime of the process. On a long-running server this file grows unboundedly — a year of 30-minute flushes produces ~17,500 rows, and there is no automated mechanism to rotate or prune old data. Manual intervention is required to control disk usage, and a single corrupt or oversized file can block the entire analytics read path.
  - **Why:** The analytics layer is meant to be a lightweight, zero-maintenance observability tool. Unbounded file growth undermines that guarantee and creates an operational risk for any deployment that runs beyond a few months. Disk pressure from stale analytics data should never require human intervention.
  - **Expected Outcome:** `CsvAnalyticsStore` generates its file path from the current UTC date at construction time (e.g. `metrics_2026-06-08.csv`), so each calendar day produces its own file. A janitor function runs once on startup and once per week thereafter; it scans the metrics directory and permanently deletes any `.csv` file whose date suffix is older than 30 days. The scheduler and report query layer are updated to read across multiple date-named files when a query range spans day boundaries. No behavior changes for the live metrics endpoint or email reports.
  - **Note:** CSV-specific mitigation only. If BL-ANALYTICS-02 (Supabase) is adopted, this item becomes obsolete — skip it and prioritize BL-ANALYTICS-02 instead.

- [ ] **BL-ANALYTICS-QUERY-01** `CsvAnalyticsStore.queryRows` reads the entire CSV file on every API call
  - **Current Issue:** Every call to `queryRows` — triggered by `/admin/history` requests and all three report generators — calls `readFileSync` on the full CSV file regardless of the requested time range. At 48 bytes/row × 48 rows/day the file reaches ~840 KB after one year. A 24h dashboard query that expects ~48 rows scans and parses the full multi-year history. Concurrent midnight report generation (daily + weekly + monthly firing together) loads three separate full-file copies into memory simultaneously.
  - **Why:** As the CSV grows, query latency and peak RSS degrade proportionally. This item warrants a targeted short-term fix if Supabase adoption is deferred.
  - **Expected Outcome:** Cache the file contents by modification timestamp — serve subsequent `queryRows` calls from the in-memory copy until the file is modified. Invalidate the cache on each `writeSnapshot`. Eliminates redundant full-file reads under the dashboard's polling load.
  - **Note:** Short-term mitigation only. Superseded by BL-ANALYTICS-02 (Supabase), which eliminates file I/O from query paths entirely. Skip this item if BL-ANALYTICS-02 is prioritized.

- [ ] **BL-CSV-COLUMNS-01** Frontend CSV export column order silently depends on backend JSON key order
  - **Current Issue:** `ReportControls.tsx` derives CSV headers from `Object.keys(rows[0])` — i.e., whatever serialization order the backend's `PeriodicRow` object literal happens to have. It matches the backend's `CSV_COLUMNS` constant today, but any reordering or added field in the backend object literal would silently reorder or misalign the exported CSV columns with no error.
  - **Why:** A silently reordered CSV is worse than a failing one — downstream spreadsheets and scripts keyed to column positions read wrong values without any signal. The backend already maintains the authoritative `CSV_COLUMNS` list; the frontend duplicating that knowledge implicitly is an invisible coupling.
  - **Expected Outcome:** A shared column list (e.g., exported from `shared/` and imported by both `backend/src/admin/analytics.ts` and `frontend/src/features/admin/ReportControls.tsx`) pins the export order. The frontend CSV export iterates that list rather than `Object.keys`. Relates to T6.8-12 (CSV export column-order verification).
  - **Note:** CSV-specific fix. If BL-ANALYTICS-02 (Supabase) is adopted and the frontend export moves to a non-CSV format, this item becomes obsolete.

- [ ] **BL-CSV-TIMESTAMP-01** CSV attachment timestamp columns display as Unix epoch integers instead of readable datetime strings
  - **Current Issue:** The `recordedAt` and `processStartedAt` columns in the daily report CSV attachment show raw millisecond epoch values (e.g., `1781196816629`) rather than human-readable strings. Spreadsheet applications (Excel, Google Sheets) interpret these as plain numbers, not dates, making the columns unreadable without manual conversion.
  - **Why:** The primary consumer of the CSV is a human operator viewing it in a spreadsheet. Epoch integers carry no operational value there — the operator cannot tell whether a reading was taken at 2 AM or 2 PM, or how far apart two rows are. The formatting bug defeats the self-evident nature of the data.
  - **Expected Outcome:** `buildCsv` converts `recordedAt` and `processStartedAt` epoch values to ISO 8601 strings (e.g., `2026-06-12T14:30:00Z`) before writing each CSV row. The resulting values parse natively as dates in spreadsheet tools. No changes to the in-memory `PeriodicRow` type — conversion is formatting-only at the serialization boundary.
  - **Note:** CSV-specific fix. If BL-ANALYTICS-02 (Supabase) is adopted and email report attachments move to a different format, re-evaluate whether this fix is still needed.

- [ ] **BL-SIG-EMPTY-ROOM-TIMER-01** liveCount=0 path does not start the 15-min empty-room timer (covers disconnect and last-guest leave)
  - **Current Issue:** When a room reaches `liveCount === 0` — every participant drops via unexpected disconnect, or the last live guest explicitly `leave_room`s while the host is in grace — the `SOLO_ROOM_TIMEOUT_MS` (15-min) timer is never started; the restart branch only fires at `liveCount === 1`. On disconnect the room then persists until the 60-min host or 30-min guest grace fires; on leave the room is instead destroyed immediately with the wrong reason (see BL-SIG-LEAVE-EMPTY-REASON-01).
  - **Why:** Per the lifecycle spec (lifecycle.md §1 Rule 5 and §3), any `liveCount`→0 (other than host explicit leave, which is immediate `host_left`) must start/continue the 15-min empty-room timer, cancelling any existing solo timer first. If nobody returns before it fires, destroy with `solo_timeout_expired`. Grace windows continue in parallel; the earliest deadline wins. This enforces a tight bound on fully-empty rooms while still honoring the host's reconnect window.
  - **Expected Outcome:** In the host-disconnect, guest-disconnect, and guest-leave paths, when the resulting `liveCount === 0`, (re)start the `SOLO_ROOM_TIMEOUT_MS` timer (cancel any running solo timer first) rather than destroying immediately. If any participant returns (`liveCount` ≥ 1) before it fires, cancel/restart per lifecycle.md §1 Rule 8. If it fires, destroy with `solo_timeout_expired`. Supersedes the immediate-destroy behavior tracked in BL-SIG-LEAVE-EMPTY-REASON-01.

## Signaling & Protocol


- [ ] **BL-ARCH-STATE-MODEL-01** Design §3 context module types not yet verified against current handler implementations
  - **Current Issue:** `core-architecture.md` §3 now describes the correct high-level structure (context modules own auth, grace/TTL, reconnect, rate-limit state), but the exact type definitions for `PasswordAuthContext`, `GraceWindowContext`, `ReconnectContext`, and `RateLimitingContext` have not been verified against the current handler source files (`passwordAuth.ts`, `graceWindowManager.ts`, `reconnectionManager.ts`, `rateLimiting.ts`).

- [ ] **BL-SIG-SOLO-GUEST-OWNER-01** Solo timer is armed for guest-occupied rooms, truncating host grace and contradicting the host-only resume guard 🔴 **Severity: High** *(Phase 10 code review)*
  - **Current Issue:** `restartSoloTimerIfSolo` (`registerSocketHandlers.ts:249`) arms the 15-min solo timer whenever `getLiveParticipantCount === 1`, with no check that the lone live participant is the host. It is called from host-disconnect (`:970`), leave (`:921`), kick (`:881`), and guest-disconnect (`:1000`). The `resume_session` path (`:659-667`) explicitly treats the solo policy as host-only ("must not reset the deadline or be handed a `soloDeadlineAt` it doesn't own") and only restarts for `isHostResuming`. The arming paths and the resume path therefore disagree about who "solo" applies to. Compounding this: when a guest resumes as the sole live participant (`resumeLiveCount === 1 && !isHostResuming`), neither resume branch clears a stale solo timer — it keeps running while `room_joined` reports `soloDeadlineAt: null`.
  - **Why:** When a host disconnects leaving one guest, `beginHostGrace` arms a 60-min `host_grace_expired` timer but `restartSoloTimerIfSolo` also arms a 15-min `solo_timeout_expired` timer and emits a host-owned `soloDeadlineAt` to the guest. The solo timer fires first and destroys the room ~45 min before the host's grace window closes, truncating host reconnect to 15 min and defeating the host-ownership lifetime model.
  - **Decision (2026-06-26, user-confirmed):** Solo applies to **any single live participant** (host or guest) per lifecycle.md §1 Rule 8. The "host-owns-solo" framing was legacy and is not the intended model; host grace may legitimately be truncated by the solo timer.
  - **Expected Outcome:** Remove the `isHostResuming` special-casing in the `resume_session` solo branch so a guest resuming as the sole live participant also (re)starts the solo timer and is sent `soloDeadlineAt`; never leave a stale solo timer running while `room_joined` reports `soloDeadlineAt: null`. The four arming sites (host-disconnect/leave/kick/guest-disconnect) already implement any-solo and remain unchanged. All five paths agree: one live participant = solo timer active.

- [ ] **BL-SIG-ROOMFULL-GHOST-01** `ROOM_FULL` capacity gate counts in-grace disconnected sentinels, blocking legitimate joiners 🟠 **Severity: Medium** *(Phase 10 code review)*
  - **Current Issue:** The `ROOM_FULL` gate (`registerSocketHandlers.ts:496`) and the `room_created` count (`:396`) use `room.participants.size`, which includes `disconnected:` sentinels held during a 30–60 min grace window, while clients are sent the live count.
  - **Why:** A legitimate new joiner with a different nickname is rejected with `ROOM_FULL` for up to the grace window even though fewer than `MAX_PARTICIPANTS_PER_ROOM` are live — the nickname-eviction path frees the slot only when the newcomer reuses the dead holder's exact nickname. Server capacity and the client-displayed live count also diverge.
  - **Expected Outcome:** Decide whether grace slots are reserved by design (then surface "reserved" in the UI) or whether the cap should gate on `getLiveParticipantCount`. Make the capacity check and the displayed count use the same measure.

- [ ] **BL-WEBRTC-SYNCPEERS-RACE-01** `onPeerLeft` mesh-repair reads stale React state, potentially pruning a newly-joined peer's connection 🟠 **Severity: Medium** *(Phase 10 code review)*
  - **Current Issue:** `onPeerLeft` ([useVaporRoom.ts:339](../../frontend/src/features/room/useVaporRoom.ts#L339)) derives `remainingPeerIds` from `stateRef.current.participants` then calls `peerMeshRef.current?.syncPeers(remainingPeerIds)`, which prunes any peer connection not in the provided set. `onPeerJoined` updates `participants` via async `setState` but adds the peer to the mesh synchronously (`handlePeerJoined`). If a `peer_left` fires before the `peer_joined` `setState` commits, `stateRef.current.participants` does not yet include the new peer, causing `syncPeers` to call `removePeer` on its active connection.
  - **Why:** The repair pass VP-10.2 introduced a new race. Peer connection/disconnection edge cases (simultaneous join+leave, host departure, multi-party topology changes) recur across phases — the system design section on multi-party topology changes needs explicit sequencing rules to prevent recurrence.
  - **Expected Outcome:** Either derive `remainingPeerIds` from within the `setState` callback (after `withPeerLeft` runs), or limit the repair-pass `syncPeers` to adding missing connections without pruning. Document the intended sequencing invariant in the system design.

- [ ] **BL-RESUME-DEAD-ROOM-UI-01** Resume failures with `RECONNECT_TOKEN_STALE` / `HOST_RECONNECT_WINDOW_EXPIRED` leave client stuck on room screen with no UI transition 🟠 **Severity: Medium** *(Phase 10 code review)*
  - **Current Issue:** `onError` ([useVaporRoom.ts:459](../../frontend/src/features/room/useVaporRoom.ts#L459)) clears the chat snapshot and reconnect token for these two codes but does not call `resetToLobby` or `withRoomEnded`. The client stays on `screen === 'room'` with a live-but-useless peer mesh and no path back to the lobby except a manual page refresh.
  - **Why:** These two codes mean the room/grace is definitively gone — the same terminal state as `ROOM_NOT_FOUND`. Leaving the UI in the room screen with no indication is misleading and blocks the user.
  - **Expected Outcome:** A flowchart mapping all resume-failure codes to their correct UI transitions should be authored first. The fix likely mirrors `ROOM_NOT_FOUND` (call `resetToLobby` or `withRoomEnded`) but the exact transition for each code should be agreed at the design level.

- [ ] **BL-WEBRTC-CLOSED-CHANNEL-REUSE-01** Mesh repair (`syncPeers`) silently skips data channel creation when a closed channel still occupies `dataChannels` 🟡 **Severity: Low** *(Phase 10 code review)*
  - **Current Issue:** When a data channel's `onclose` fires without the `RTCPeerConnection` failing, `removePeer` is never called and the `'closed'` channel remains in `dataChannels`. On the next `syncPeers` repair pass, `needsOffer` correctly returns `true` (channel not open/connecting, signalingState stable), but `startOffer`'s guard `if (!this.dataChannels.has(peerId))` skips creating a new channel. The renegotiated offer therefore carries no usable data channel.
  - **Why:** A peer whose data channel quietly closed ends up with a healthy `RTCPeerConnection` but no working channel after a repair pass, silently preventing message delivery — the exact scenario VP-10.2 intended to repair.
  - **Expected Outcome:** Before calling `startOffer`, remove any `'closed'` or `'closing'` channel from `dataChannels` so the fresh offer creates a new one. Alternatively, call `removePeer` from `channel.onclose`.

  - **Why:** Dead debug code adds noise and a `const false` guard is less intentional than a build-time strip. A future developer may not realise the feature is permanently off.
  - **Expected Outcome:** Remove `DEBUG_PEER_TRACE` and `tracePeer`, or replace the constant with a build-time check (`import.meta.env.DEV`) so the function is stripped in production builds.

- [ ] **BL-REFACTOR-CHAT-PERSIST-PERF-01** Chat persistence effect serializes the full message array on every append (O(n) per message) 🟡 **Severity: Low** *(Phase 10 refactoring)*
  - **Current Issue:** `useEffect` in `useVaporRoom.ts` calls `saveChatHistory(state.activeRoomId, state.chatMessages)` on every `state.chatMessages` change, running `JSON.stringify` over the full array each time a single message is appended.
  - **Why:** For long sessions the serialization cost grows linearly with message count and runs on every React commit that appends a message.
  - **Expected Outcome:** Debounce or throttle the `saveChatHistory` write (e.g. 300–500 ms) so rapid back-to-back appends produce a single storage write rather than one per message.

- [ ] **BL-REFACTOR-SESSION-TEARDOWN-01** Terminal session teardown triple (`clearChatHistory` + `clearStoredReconnectSession` + `clearRoomSession`) repeated at five call sites 🟡 **Severity: Low** *(Phase 10 refactoring)*
  - **Current Issue:** `leaveRoom`, `backToLobby`, `onParticipantKicked`, `onRoomDestroyed`, and the `onError` auto-resume branch each call all three teardown operations (with minor per-site variations). Drift in this pattern already produced a confirmed bug in this phase (OOS-P10-2) where two error codes cleared storage but omitted the UI transition.
  - **Why:** Any future change to the teardown sequence (e.g. a new piece of state to clear) must be applied at all five sites independently. Missing one site causes subtle state leaks.
  - **Expected Outcome:** Extract a `teardownLocalSession(roomId: string | null | undefined)` helper that calls all three operations. All five call sites use it. Per-site differences (e.g. socket disconnect for kick) are performed outside the helper.

## Product Features

- [ ] **BL-FILE-01** P2P file sharing readiness (signaling/UI hooks)
  - **Current Issue:** Vapor supports real-time text chat over WebRTC data channels but has no mechanism for participants to exchange files. Sharing a file requires leaving Vapor and using an external service, breaking the ephemeral, self-contained session experience.
  - **Why:** File sharing is a natural extension of P2P chat and is uniquely suited to Vapor's architecture — WebRTC data channels can transfer binary payloads directly between peers with no server relay, preserving the zero-persistence guarantee. Establishing the signaling scaffolding and UI hooks now creates the pattern for a complete implementation without a full protocol redesign.
  - **Expected Outcome:** A file-selection UI element in the chat room initiates a WebRTC data-channel file transfer to the targeted peer(s). The signaling layer includes hooks for file transfer negotiation (offer/accept/reject). Transfer progress is visible in the UI. No file content touches the signaling server at any point.

- [ ] **BL-CHAT-PERSIST-RAM-01** Optional RAM-only chat history for reconnecting participants
  - **Current Issue:** Chat messages are delivered to peers via WebRTC data channels in real time and exist only in each client's local state. When a participant disconnects and reconnects within the host's grace window, the data channel resets and all prior messages are lost — they rejoin with an empty chat view and cannot catch up on what was discussed.
  - **Why:** Losing chat history on reconnect degrades the session experience for participants who have brief network drops. Since Vapor already supports host reconnect grace windows, participants expect to resume the session meaningfully — but rejoining with an empty chat is jarring and reduces the practical utility of reconnect support.
  - **Expected Outcome:** The host's client maintains an in-memory circular buffer of recent chat messages (e.g., last 50 messages, configurable). On peer reconnect, the host replays the buffer over the newly established data channel before resuming live delivery. No messages are stored server-side; the buffer lives only in the host's browser memory for the room's lifetime and is discarded when the room is destroyed.
  - **Relationship to VP-10.4:** Phase 10 VP-10.4 restores a reconnecting peer's *own* pre-disconnect history from local `sessionStorage`; it does **not** backfill messages other peers sent *during* the offline gap. This item is the future feature that closes that gap (host-side replay buffer) — offline-window messages are out of scope until it lands.

- [ ] **BL-FEAT-ROOM-LOCK-01** Host can lock a room to refuse new participants regardless of remaining capacity
  - **Current Issue:** A room accepts new joiners until it reaches `MAX_PARTICIPANTS_PER_ROOM` (5). A host has no way to seal the room earlier — e.g. once the intended people are present — so anyone with the room ID/name (and password, if set) can still take a free slot.
  - **Why:** Hosts want control over who is in the room once a conversation is underway. Closing the room to further joins while capacity remains is a common privacy/moderation expectation and reinforces Vapor's host-sovereign model. It is distinct from a password: a locked open room admits nobody new; a locked protected room refuses even password-holders.
  - **Expected Outcome:** A host-only control toggles a per-room `locked` flag (lock/unlock, reversible) held in RAM alongside the `RoomRecord`. While locked, `join_room` is rejected even when `liveCount < MAX_PARTICIPANTS_PER_ROOM`; `resume_session` for an existing in-grace participant is still honored (a lock blocks *new* joiners, not reconnects). The host UI reflects lock state.
  - **Open design questions (resolve at phase planning):** (1) Which rejection code — reuse `ROOM_FULL`, or add a new code (the error set in CLAUDE.md §2 is intentionally restricted: ROOM_NOT_FOUND, ROOM_FULL, ROOM_EXPIRED, INVALID_PASSWORD, HOST_RECONNECT_WINDOW_EXPIRED, RECONNECT_TOKEN_STALE, RATE_LIMITED, INVALID_SIGNAL_PAYLOAD, NOT_AUTHORIZED)? (2) New signaling events (e.g. `lock_room`/`unlock_room`) vs. a parameter on an existing host action — note the contract in CLAUDE.md §6 would need updating either way. (3) Whether lock state is surfaced to existing guests or kept host-only. (4) Default state on room creation (unlocked).

- [ ] **BL-FEAT-LASTSEEN-01** Surface participant `lastSeenAt` activity to users *(stub — detail to be added; from Phase 11 CR11-9)*
  - **Current Issue:** `ParticipantRecord.lastSeenAt` is maintained in RAM — set at create/join (`roomLifecycle.ts:32,67`) and refreshed on every successful `signal_offer`/`signal_answer`/`signal_ice` relay (`signalRelay.ts:96`) — but **no production code reads it** after the heartbeat mechanism was removed in Phase 11 (VP-11.7). It is currently write-only state with no consumer; it is read only by test `T11.7-04`.
  - **Why:** The field is intentionally retained (user decision, 2026-06-30) because participant activity / "last seen" is useful information to surface to users, but the consuming feature does not exist yet. Keeping the write path live now means the data is already accurate whenever the feature is built.
  - **Expected Outcome:** *(to be detailed by the user)* — define how participant activity is surfaced (e.g. a per-participant "active"/"idle"/"last active N min ago" indicator in the roster), the wire mechanism to deliver it to clients (it is server-side state today and not in any payload), and the privacy posture given the zero-persistence model. Two technical notes to fold in when scoping: (a) decide whether the relay stamp should move to **after** payload validation so `lastSeenAt` reflects only fully-valid signals (today it is stamped in `resolveSignalRoute` before SDP/candidate normalization — see CR11-9); (b) confirm exposing activity timestamps does not leak presence in a way that contradicts the ephemerality guarantees.

## User Experience

- [ ] **BL-UX-KICK-SOLO-TIMER-01** Solo timer does not restart when an explicit guest leave reduces liveCount to 1
  - **Current Issue:** The `leaveRoom` handler does not restart the solo timer when `liveCount` drops to 1 after a guest explicitly leaves. The kick handler was fully fixed in Phase 9 and correctly restarts the timer when `remainingCount === 1` without any guard flag. The gap is exclusively in the `leaveRoom` path — the host sees no countdown and the room runs until TTL after a voluntary guest exit.
  - **Why:** The solo timeout reclaims idle rooms where only one participant remains. Without a restart after a voluntary leave, rooms linger far beyond the 15-min window defined in the spec, wasting RAM and misleading the host about the room's actual expiry.
  - **Expected Outcome:** In the `leaveRoom` handler, when `liveCount === 1` after a guest leaves, cancel any running solo timer and start a fresh `SOLO_ROOM_TIMEOUT_MS` one, emitting the updated `soloHostDeadlineAt` in the `peer_left` payload. No other changes needed — the kick handler already has the correct behavior.

- [ ] **BL-UX-MOBILE-CHIP-VIEWPORT-01** `RoomLifetimeChip` may overlap chat input on small mobile viewports after input-focus guard removal 🟡 **Severity: Low** *(Phase 10 code review)*
  - **Current Issue:** The focus guard that prevented `RoomLifetimeChip` from overlapping the mobile keyboard was removed in Phase 10 VP-10.3 as an intentional design simplification (alongside the `App.tsx` `min-h-dvh` → `h-dvh` layout change). The removal has not been verified on a real small-viewport mobile device.
  - **Why:** The guard existed because without it the chip can sit on top of the chat input when the software keyboard is open on small screens. A layout simplification that silently reintroduces an overlap regression is a UX regression that won't be caught by automated tests.
  - **Expected Outcome:** Manually verify on a small-viewport mobile device (or equivalent emulation) that `RoomLifetimeChip` does not overlap the chat input when the keyboard is open. If overlap exists, adopt an alternative layout fix (e.g. CSS-only solution or conditional positioning) without reintroducing the JS focus listener.

- [ ] **BL-UX-TIMER-DOUBLE-COUNTDOWN-01** Solo deadline drives two chips at once; lifetime chip conflates three deadlines 🟠 **Severity: Medium** *(Phase 10 code review)*
  - **Current Issue:** `derived.soloDeadlineAt` (`useVaporRoom.ts:641`) feeds `SoloWaitingChip`, while `derived.expiresAt = Math.min(expiresAt, hostReconnectGraceDeadlineAt, soloDeadlineAt)` (`:588-593`) feeds `RoomLifetimeChip`; both chips render together (`RoomView.tsx:626-627`, `RoomViewDesktop.tsx:473-474`). When a solo deadline is active it is the smallest value, so both chips count down the same instant. Folding `hostReconnectGraceDeadlineAt` into the lifetime value similarly makes "Ends in" jump to the grace deadline on host disconnect.
  - **Why:** Two chips showing the same countdown is redundant and confusing; mixing three semantically different deadlines (room TTL, host grace, solo) into one "room ends" number misrepresents room expiry. Related to VP-10.4 (timer reliability).
  - **Expected Outcome:** Exclude `soloDeadlineAt` from the lifetime `Math.min` now that `SoloWaitingChip` surfaces it, and reconsider whether `hostReconnectGraceDeadlineAt` belongs in the lifetime number. Each deadline is shown by exactly one widget.
