# Phase 7 — Detailed Work Matrix

Date: 2026-06-12 (revised 2026-06-15 after design review)

## Purpose
Phase 7 redesigns the participant-facing UI (LobbyView, RoomView, app shell) using the Stitch reference mockups ([LobbyView_Stitch.jpg](/docs/UI_design/reference/LobbyView_Stitch.jpg), [RoomView_Stitich.jpg](/docs/UI_design/reference/RoomView_Stitich.jpg)) as the **layout direction — not a pixel-perfect spec, and not a colour spec**. Button treatment, component composition, spacing, and typography follow the reference; the reference's soft light aesthetic becomes the `light` theme, while the shipped default is the `blue` theme (see D-1). Existing behavior does not change. Phase 7 also introduces a simple, user-selectable **Theme** system (Light, Dark, Blue) — a personal client-side preference, zero server involvement.

> **Revision note (2026-06-15, design review):** The original "Atmosphere" concept (host-broadcast Mist/Ash/Ember presets over the WebRTC data channel) is **dropped** in favour of a plain per-user, client-side theme choice (see D-1, D-6). The `data-atmosphere` attribute became `data-theme` (now on `<html>`); the mist palette became the `light` theme; the shipped default is the `blue` theme. The review also added the **mobile-constrained app column** (folded into VP-7.1 as 7.1.10–7.1.11) and the **Privacy/FAQ info-page restructure** (VP-7.3). VP-7.2 is rewritten accordingly below.

### Design Direction Decisions (binding for this phase)

| # | Decision | Rationale |
|---|---|---|
| D-1 | The Stitch reference defines **layout, composition, and component language — not the colour palette**. Vapor ships **three** user-selectable themes: `light`, `dark`, and **`blue` (default)**. The `light` theme adopts the reference's soft, light aesthetic (renamed from the original `mist`); `blue` is a deep `#006699`-based palette and is the shipped default. The "atmosphere" naming and the Mist/Ash/Ember presets are retired. | The reference is directional for layout; colour is a separate, user-chosen concern. A small fixed theme set keeps the product simple. |
| D-2 | **No behavioral changes.** The create/join mode toggle, nickname field, password semantics, participant kick, typing indicator, diagnostics overlay (Ctrl+Shift+D), solo/lifetime chips, and copy-room-ID all keep their current behavior — only their visual treatment changes. | VP-7.1 expected outcome in Todo.md explicitly scopes out behavior. |
| D-3 | The Stitch **bottom navigation bar (Lobby / Chat / Setup) is NOT adopted.** It is a mobile-app pattern with no functional backing in Vapor; introducing dead navigation contradicts the minimal product. The top NavBar is restyled instead. | Reference is directional; adopt hierarchy and tone, not literal chrome. |
| D-4 | The Stitch lobby shows side-stacked "Create Room" / "Join Room" CTAs; Vapor keeps the **explicit mode toggle + single primary CTA** (restyled as a segmented control + filled pill button) because the nickname/password/room-ID field set depends on the selected mode. | Preserves current form logic (D-2) while matching the reference's button language. |
| D-5 | All theme-dependent values (gradient stops, smoke-layer hues, accent tints) must route through **CSS custom properties keyed off a `data-theme` attribute** so theme presets are pure CSS variable swaps with no component re-render. | One token foundation serves every theme; avoids retrofitting theming after the redesign. |
| D-6 | **Themes are a personal, client-side preference**, not a room-wide or host-controlled setting. Each user picks their own theme; it applies to their browser only, on every page (lobby, room, info). The choice is persisted in **`sessionStorage` only** (consistent with reconnect-token storage; cleared when the tab closes). **No backend, no socket event, no WebRTC data-channel message, no `localStorage`.** The originally-planned `theme_change` broadcast protocol is removed. | Simplicity + zero-persistence: a UI preference, not shared session data. Signaling contract stays frozen. |
| D-7 | The app is **constrained to a mobile-like column** (a centered phone-style panel, ~`min(100%, 26rem)` wide) on all viewport sizes, rather than stretching cards across a wide desktop page. The message feed scrolls inside the panel; the page does not grow. | A chat service should feel like an app panel and support multi-tasking; wide-ratio chat is uncomfortable (review point 1). |

### VP-7.1 Implementation Notes

Out-of-phase concerns/feedback only — implementation detail lives in the subtask table above.

- **`vite.config.ts` `chunkSizeWarningLimit` raised to 1000 kB:** The production bundle is a single ~887 kB chunk (270 kB gzipped). Vite's default 500 kB warning fires because `recharts` (admin) and `react-markdown`/`remark-gfm` (info pages) are statically imported alongside the main app. Lazy-loading (`React.lazy`) was considered and deliberately deferred — all three heavy deps are behind existing route boundaries that could support it, but introducing Suspense fallbacks and dynamic-import failure modes adds complexity that is not justified for rare routes in a small app. The 1000 kB limit is an honest acknowledgement of the current bundle composition, not a performance regression gate bypass.
- Pre-existing build/lint breakage at HEAD `5f548ec` was fixed in passing while landing 7.1.1–7.1.8.
- **Out-of-scope lint/type cleanups landed in passing to get `tsc -b` / `npm run build` green (resolves backlog item BL-FRONTEND-TYPES-01):** removed unused imports in `room-socket-client.ts` and `types.ts`; converted empty `interface … extends Required<…>` declarations to `type =` aliases in `types.ts`; added `void` to the floating `startOffer` promises and an explicit `RTCStats` annotation in `webrtc-chat-mesh.ts`; added a typed cast for the runtime-only `pong` manager event in `room-socket-client.ts`. **No signaling-contract, socket-event, or payload change — D-6 contract freeze preserved.**
- **`useSocketConnection.ts`:** handler/dispose ref writes moved out of render into a deps-less `useEffect` (clears the `react-hooks/refs` "Cannot update ref during render" rule in that file) and the unused `socketRef` return was removed. Behavior-neutral (socket callbacks fire post-commit).
- The same `react-hooks/refs` pattern remains in `useVaporRoom.ts` (4 errors + 6 `exhaustive-deps` warnings) — these are the only remaining `frontend/` lint failures and stay tracked as backlog item **BL-FRONTEND-LINT-REFS-01** (deliberately deferred: `useVaporRoom` is the timing-sensitive socket/WebRTC session hook; moving its ref writes must be validated against the gated room test suites). Pass criterion T7.1-01/7.1.9 is therefore satisfied as **clean on all phase-7-touched files**, not globally green lint.
